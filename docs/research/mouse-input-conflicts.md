# macOS mouse-input conflict candidates

Researched 2026-09-04 using only product-owned websites, support documentation, and official source repositories. This note is intentionally conservative: an identifier is included only when a primary source verifies it, and a running process is treated as a compatibility warning rather than proof that a particular button is intercepted.

## Executive conclusion

Spinnet can safely detect known applications or helpers and warn that they *may* compete for global middle/extra-button input. It cannot infer the user's active button assignments merely from an installed bundle or running helper. The warning should therefore name the detected utility, identify the Spinnet trigger button, and ask the user to remove actions for that same physical button in the other utility before retrying.

The safest general remediation is to give one utility exclusive ownership of each physical mouse button. Do not automatically terminate helpers, modify another application's preferences, reset Accessibility/Input Monitoring, or instruct users to uninstall a utility when removing one overlapping button assignment is sufficient.

## Products not yet safe to identify automatically

The initial review did not establish both reliable identifiers and relevant first-party behavior evidence for **USB Overdrive** and **SensibleSideButtons**. They remain plausible compatibility candidates, but Spinnet should not add guessed bundle IDs or process names. A future pass should inspect a current vendor-signed application bundle or an official build manifest and cite that exact artifact before adding detection.

## Recommended Spinnet warning model

1. Match running applications by verified bundle identifier using `NSRunningApplication`; where a helper identity is verified, inspect the helper separately. Installation alone should produce at most a lower-severity notice.
2. Display: “`<utility>` is running and can remap `<configured button>`. If triggering or Click & Drag is unreliable, remove that button's click/drag/scroll assignments in `<utility>`.”
3. Offer **Learn how** instructions specific to the detected product and **Test again**. Do not claim “button is occupied” unless Spinnet later gains direct event-path diagnostics that prove suppression or rewriting.
4. Show one consolidated warning when several candidates are present. Never request additional Accessibility permission merely because another utility is detected.
5. Keep the warning dismissible and remember dismissal by product identity and major version so it can reappear when the competing utility materially changes.

## Confidence limits

- Bundle IDs can change between major releases, distribution channels, or helper redesigns. Detection should be versioned and fail open.
- A foreground-app exclusion is not a complete solution for a global radial menu: when Spinnet is invoked, another application is usually still frontmost.
- Event-tap ordering is not an ownership protocol. Two trusted applications can observe, delay, rewrite, or suppress the same input, and neither can reliably negotiate priority through public macOS APIs.
- The presence of a mouse utility is not itself a conflict. The actionable condition is overlapping handling of the same physical button and gesture family.

## Binding-aware detection

This section records only persisted-binding details established by the completed primary-source review. A product supporting mouse-button actions does **not** imply that its private on-disk configuration is a stable interface. Spinnet must fail open: if the exact preference domain or file, schema, button-number mapping, and active-profile resolution are not all verified, that product must not produce a binding-aware warning.

### Implementation gate

Binding-aware detection is enabled only for the locally verified Mac Mouse Fix schema 24 and remains disabled for the other products. Before enabling another product, record a source-revision-pinned specification for every required field, add fixtures covering global, device-specific, and application-specific profiles, and use read-only access that neither launches the utility nor mutates or migrates its preferences. Unknown versions, unreadable data, schema mismatches, and ambiguous profile precedence must return “unknown/no warning,” never “conflict.”
